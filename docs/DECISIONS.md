# Архитектурные решения

## ADR-001: C#/.NET WinForms для технического overlay-прототипа

Статус: принято для этапов 0–1, пересмотр после проверки этапа 2.

Контекст: исходное окружение не содержало Godot, .NET SDK или C/C++ toolchain.
Главный ранний риск — прозрачное overlay-окно с выборочным захватом мыши и низким
потреблением ресурсов. Для его проверки не нужны сцены, импорт ресурсов и
скелетный renderer Godot.

Решение: использовать self-contained C#/.NET WinForms runtime и прямой
Win32-адаптер. Доменный конечный автомат, физика и формат данных не зависят от
WinForms. Это позволяет сохранить текущий runtime либо позднее заменить только
renderer/scene host на Godot.

Сравнение:

| Вариант | Плюсы | Риски на первом этапе |
|---|---|---|
| Godot 4 + C# | сильная 2D-анимация и editor | дополнительный runtime; overlay и selective click-through всё равно требуют Win32-проверки |
| WinForms + Win32 | минимальный слой, простой self-contained publish, зрелый tray | нет готового skeletal renderer; `TransparencyKey` ограничивает качество краёв |
| Electron | быстрый UI | лишний вес и память; неудобная физика и Win32 hit-testing |

Ограничение: текущая прозрачность основана на `TransparencyKey`. До работы с
фотографическими альфа-краями необходимо проверить per-pixel layered window
(`UpdateLayeredWindow`) либо Godot viewport.

Дополнение (2026-08-02): этап 2 подтвердил самый рискованный элемент (overlay +
selective click-through + физика окон), что и было условием пересмотра этого
ADR. Пользователь решил переоценить Godot 4 + C# именно для визуального
rig renderer этапа 3, поскольку GDI+/`TransparencyKey` не даёт качественной
skeletal-анимации. Поведение и state machine (инкремент 3a: run/sit,
взгляд на курсор, интенсивность) реализованы на текущем WinForms runtime — это
не зависит от выбора движка. Миграция рендерера (инкремент 3b) требует
отдельного scoping: заменить только renderer/scene host, сохранив
`DesktopPeople.Core` (state machine, physics, platform geometry) как есть, либо
перенести весь runtime. Решение по объёму миграции не принято.

## ADR-002: тестовый runner без внешних test-пакетов

Статус: принято.

Unit-проверки используют маленький консольный runner и стандартную библиотеку.
Это обеспечивает сборку без NuGet и сети. Когда появится обоснованная внешняя
инфраструктура пакетов, runner можно перенести на xUnit/NUnit без изменения
тестируемого ядра.

Обычная сборка и тесты не загружают пакеты. Self-contained публикация получает
официальные redistributable runtime packs .NET с `nuget.org`; это build-time
операция и не добавляет сетевого кода в приложение.

## ADR-003: .NET 10 LTS и self-contained win-x64

Статус: принято.

Разработка использует .NET 10. Release-публикация включает runtime, поэтому
конечному пользователю не требуется отдельно устанавливать .NET. Приложение
запрашивает обычные пользовательские права (`asInvoker`).

## ADR-004: event-driven Windows platforms с редкой сверкой

Статус: принято.

Первый snapshot строится через `EnumWindows`. Системные события передаются через
thread-safe очередь и обновляют только затронутое окно; полная сверка выполняется
раз в пять секунд. Физика получает immutable модели без Win32-структур.

Для перекрытия применяется отдельная консервативная policy верхних сегментов.
Она лучше полного игнорирования z-order, но не считается полной visible-region
композицией shaped/layered окон.

Дополнение (2026-08-02): изначальный набор хуков не включал
`EVENT_SYSTEM_FOREGROUND`, поэтому смена z-order при переключении фокуса между
окнами обновлялась только на плановой пятисекундной сверке — персонаж мог
несколько секунд стоять там, где раньше было окно, потерявшее фокус. Хук
добавлен; при получении события provider форсирует немедленный `Reconcile`
вместо ожидания интервала, сохраняя остальную event-driven модель без изменений.
