# Архитектурные решения

## ADR-001: C#/.NET WinForms для технического overlay-прототипа

Статус: принято для этапов 0–1, пересмотр после проверки этапа 2.

Контекст: исходное окружение не содержало Godot, .NET SDK или C/C++ toolchain.
Главный ранний риск — прозрачное overlay-окно с выборочным захватом мыши и низким
потреблением ресурсов. Для его проверки не нужны сцены, импорт ресурсов и
скелетный renderer Godot.

Решение: использовать self-contained C#/.NET WinForms runtime и прямой
Win32-адаптер. Доменный конечный автомат, физика и формат данных не зависят от
WinForms. Это позволяет сохранить текущий runtime либо позднее заменить только
renderer/scene host на Godot.

Сравнение:

| Вариант | Плюсы | Риски на первом этапе |
|---|---|---|
| Godot 4 + C# | сильная 2D-анимация и editor | дополнительный runtime; overlay и selective click-through всё равно требуют Win32-проверки |
| WinForms + Win32 | минимальный слой, простой self-contained publish, зрелый tray | нет готового skeletal renderer; `TransparencyKey` ограничивает качество краёв |
| Electron | быстрый UI | лишний вес и память; неудобная физика и Win32 hit-testing |

Ограничение: текущая прозрачность основана на `TransparencyKey`. До работы с
фотографическими альфа-краями необходимо проверить per-pixel layered window
(`UpdateLayeredWindow`) либо Godot viewport.

Дополнение (2026-08-02): этап 2 подтвердил самый рискованный элемент (overlay +
selective click-through + физика окон), что и было условием пересмотра этого
ADR. Пользователь решил переоценить Godot 4 + C# именно для визуального
rig renderer этапа 3, поскольку GDI+/`TransparencyKey` не даёт качественной
skeletal-анимации. Поведение и state machine (инкремент 3a: run/sit,
взгляд на курсор, интенсивность) реализованы на текущем WinForms runtime — это
не зависит от выбора движка. Миграция рендерера (инкремент 3b) требует
отдельного scoping: заменить только renderer/scene host, сохранив
`DesktopPeople.Core` (state machine, physics, platform geometry) как есть, либо
перенести весь runtime. Решение по объёму миграции не принято.

Дополнение (2026-08-03): scoping объёма миграции (инкремент 3b). Структурная
проверка показала, что `DesktopPeople.Core` (`net10.0`, без Windows-специфики)
и `DesktopPeople.Windows` (`net10.0-windows`, чистый Win32 P/Invoke —
`EnumWindows`/DWM/WinEvent-хуки, ни одной ссылки на `System.Windows.Forms`)
уже сегодня не зависят от WinForms и от `DesktopPeople.App`. Единственный
проект, завязанный на WinForms, — сам `DesktopPeople.App` (`OverlayForm`,
`Program`, `JsonLineLogger`, `CharacterRenderer`, трей, обработка мыши).

Рекомендованный объём миграции: заменить только `DesktopPeople.App` на новый
Godot 4 + C# runtime; `DesktopPeople.Core` и `DesktopPeople.Windows`
подключаются к новому Godot-проекту как обычный `ProjectReference` без
изменений. Требования, из-за которых изначально рассматривался вариант
«перенести весь runtime», по документации/форумным источникам (не пилотным
прототипом) оказались выполнимы средствами самого Godot 4:

- **Прозрачное окно + выборочный click-through**: `DisplayServer.
  window_set_mouse_passthrough(polygon)` задаёт полигон, принимающий клики
  мыши, — события за его пределами уходят окну под ним; прямой аналог
  сегодняшнего ручного переключения `WS_EX_TRANSPARENT` по факту наведения
  на силуэт персонажа, только полигон обновляется каждый кадр, а не
  бинарным вкл/выкл всего окна.
- **Иконка в трее**: начиная с godotengine/godot#80211 в Godot 4 есть
  штатный узел `StatusIndicator` (Windows/macOS; на Linux не поддержан) —
  не нужен свой P/Invoke под `Shell_NotifyIcon`.
- **Публикация одним exe**: экспорт с опцией «Embed .pck» даёт один
  self-contained `.exe`, аналог сегодняшнего `dotnet publish
  --self-contained`.
- **Win32-адаптер и физика окон**: `DesktopPeople.Windows` переносить не
  нужно — Godot C#-проект ссылается на него как на обычную .NET-библиотеку.
  Флаги `WS_EX_TOOLWINDOW`/`WS_EX_NOACTIVATE`, сегодня выставляемые через
  `OverlayForm.CreateParams`, при миграции выставляются тем же P/Invoke-кодом
  поверх нативного HWND, который Godot отдаёт через `DisplayServer.
  window_get_native_handle`.

Не проверено (требует отдельной технической проверки перед стартом миграции,
не просто чтения документации):

- точная модель пересчёта `RectD`/`Vec2` (`DesktopPeople.Core`) в координаты
  Godot при нескольких мониторах с разным DPI — сегодняшние DPI-тесты
  (`screen coordinates map into overlay coordinates` и т.д.) проверяют только
  WinForms-путь пересчёта;
- реальное поведение per-pixel transparency и mouse passthrough на
  многомониторных/mixed-DPI конфигурациях — из форумных обсуждений известны
  отдельные платформенные баги/ограничения, лично не проверялись;
- накладные расходы (CPU/память в простое) Godot-рантайма против текущих
  0.73% CPU / 71.4 МБ у WinForms-версии — конкретной цифры нет, Godot-движок
  тяжелее голого WinForms-процесса по построению;
- совместимость `StatusIndicator` с уже реализованным функционалом трея
  (переключение «Активность», show/hide launcher) — не проверялась.

Статус решения: рекомендован вариант «заменить только `App`, `Core`/`Windows`
без изменений» как реализуемый и кардинально более дешёвый, чем перенос всего
runtime, — но это вывод по документному/форумному ресёрчу, не по пилотному
прототипу на реальной multi-monitor/DPI-конфигурации. Финальное решение и
старт миграции — на усмотрение пользователя.

Дополнение (2026-08-03): pilot-спайк (Godot 4.7.1 mono, путь `C:\Godot\godot.exe`,
установлен пользователем). Проект — `godot-pilot/DesktopPeoplePilot/` (не часть
`DesktopPeople.slnx`, отдельный `Directory.Build.props` изолирует его от
строгих настроек основного решения). Подтверждено реальным запуском, не только
документацией:

- `DesktopPeoplePilot.csproj` (`Godot.NET.Sdk/4.7.1`, `TargetFramework
  net10.0-windows`) ссылается на `DesktopPeople.Core` и `DesktopPeople.Windows`
  обычными `ProjectReference` БЕЗ единого изменения в их коде — `dotnet build`
  проходит чисто. Единственная правка потребовалась в самом пилоте (TFM
  `net10.0` → `net10.0-windows`: NuGet считает голый `net10.0` несовместимым
  потребителем для `net10.0-windows`-библиотеки — ожидаемо, раз пилот всё
  равно Windows-only).
- Запущен НЕ headless (`godot.exe --path .`, Vulkan/Forward+, Intel UHD
  Graphics) — `WindowsWindowPlatformProvider` (тот же класс, что использует
  `DesktopPeopleContext` в реальном приложении) стартовал внутри
  Godot-хостинга .NET и в реальном времени опрашивал живой рабочий стол:
  `enumerated=236` окон в снапшоте, отфильтровано до 1–2 валидных платформ,
  показания менялись по ходу запуска (значит реально реагирует на живые
  изменения, а не отдаёт статичный слепок). Процесс стабилен (`Responding:
  True`), без исключений, за время наблюдения.
- **Не проверено** (нет инструмента сделать скриншот/увидеть экран в этой
  сессии): реально ли окно получилось прозрачным, действительно ли
  `DisplayServer.WindowSetMousePassthrough` даёт клик по прямоугольнику-заглушке
  и промах мимо него сквозь окно на рабочий стол, действительно ли
  `AlwaysOnTop`/`Borderless` выглядят корректно. Код по документации API
  написан и компилируется, но визуальную часть должен подтвердить пользователь
  на реальном экране — это следующий шаг, не «пилот завершён».

Вывод: главный структурный риск скоупинга (Core/Windows подключаются как есть)
подтверждён работающим кодом, а не только рассуждением. Оставшийся риск —
чисто визуальный (транспарентность/click-through/topmost), для него нужен
живой визуальный прогон пользователем.

Дополнение (2026-08-03): визуальный прогон пользователем нашёл реальный баг —
не «не проверено», а именно баг. Окно открылось непрозрачным чёрным на весь
экран, выйти из него было нельзя штатно (у пилота нет трея — не за что
кликнуть, чтобы закрыть), помог только Alt+Tab → закрыть из списка окон;
переключение на другие окна через Alt+Tab не помогало (топ-most чёрное окно
продолжало визуально всё перекрывать поверх любого окна, на которое
переключался фокус).

Причина найдена по стектрейсам/issue-трекеру Godot, не гаданием: у Forward+
(Vulkan, дефолтный rendering method в Godot 4) прозрачность окна на Windows
не работает — флаг `transparent` применяется, но композитинг всё равно
рисует сплошной непрозрачный чёрный вместо альфы. Это открытая, воспроизводимая
проблема движка (godotengine/godot#103456, #89205, #65487 — все три с тем же
симптомом «чёрное вместо прозрачного именно на Forward+»), не ошибка в коде
пилота. **Исправлено**: `project.godot` → `[rendering] renderer/rendering_method
= "gl_compatibility"` — тот же issue-трекер подтверждает, что прозрачность
работает на Compatibility-рендерере. После правки процесс на этой машине
запустился на `OpenGL API 3.3.0 ... Compatibility` (было `Vulkan 1.3.275
Forward+`) — переключение рендерера подтверждено по логу запуска, сама
прозрачность на экране — ещё нет (см. ниже).

Отдельно, независимо от причины: у throwaway-пилота не должно быть сценария
«застрял, кроме Alt+Tab выхода нет» вообще, даже если что-то опять пойдёт не
так. Добавлен явный `ESC` → `GetTree().Quit()` в `PilotOverlay._Input`, плюс
надпись на экране «press ESC to quit» рядом со stand-in прямоугольником — не
зависит от того, работает ли прозрачность/click-through на этот раз.

Дополнение (2026-08-03, продолжение): переключения рендерера ОКАЗАЛОСЬ
НЕДОСТАТОЧНО — повторный прогон пользователем дал то же чёрное окно. Нашлись
ещё две причины, обе подтверждены документацией/issue-трекером:

1. `TransparentBg` выставлялся как `window.GetViewport().TransparentBg`. На
   корневом окне (`Window` наследует `Viewport`) вызов `GetViewport()` не
   разрешается обратно в этот же самый viewport, поэтому clear color
   продолжал заливаться непрозрачным. Нужно ставить прямо на корне:
   `GetTree().Root.TransparentBg = true`. Отдельно подтверждено, что одних
   project-настроек недостаточно — этот рантайм-вызов обязателен.
2. Окно было ровно 1920x1200 — в точности нативное разрешение машины.
   Borderless-окно точно в размер экрана Windows промотирует до
   fullscreen-exclusive, а fullscreen сбрасывает per-pixel transparency в
   непрозрачный чёрный. Документированный обходной путь — сделать окно на
   один пиксель меньше; в пилоте теперь 1920x1199 + явный `window/size/mode=0`
   (windowed). **Это важно для полной миграции**: реальный оверлей сейчас
   растягивается ровно на `SystemInformation.VirtualScreen`, то есть в
   Godot-версии попадёт ровно в эту ловушку, если не заложить тот же зазор
   или явную windowed-модальность.

**Проверено визуально скриншотом** (снят программно через PowerShell/
`Graphics.CopyFromScreen`, прочитан, затем немедленно удалён — захватывал весь
экран пользователя целиком): после всех трёх правок (gl_compatibility +
`Root.TransparentBg` + недо-нативный размер) фон окна действительно
прозрачный, рабочий стол виден сквозь него, stand-in прямоугольник рисуется
на своём месте. Чёрного окна больше нет.

Дополнение (2026-08-03, итог пилота): **click-through подтверждён
пользователем** — клик мимо stand-in прямоугольника проваливается на окно под
оверлеем (фокус ввода уходит туда), клик по прямоугольнику поглощается
оверлеем. То есть выборочный click-through через
`WindowSetMousePassthrough` даёт ровно то поведение, ради которого в
WinForms-версии вручную дёргается `WS_EX_TRANSPARENT`.

При этом пользовательское описание вскрыло ещё одно расхождение с текущим
приложением: клик по прямоугольнику УВОДИЛ фокус с поля ввода. `OverlayForm`
этого не делает — она выставляет `WS_EX_NOACTIVATE` (не забирать фокус) и
`WS_EX_TOOLWINDOW` (не светиться в Alt+Tab) через `CreateParams`. У Godot
эквивалентных флагов окна нет, поэтому проверено отдельно, что до нативного
HWND можно дотянуться: `DisplayServer.WindowGetNativeHandle(HandleType.
WindowHandle)` (возвращает `long`, нужен каст в `nint`) + те же
`GetWindowLongPtr`/`SetWindowLongPtr`/`SetWindowPos`. Подтверждено по логу
запуска: ex-style `0x40018` → `0x8040098`, то есть оба бита реально
проставились на окне Godot.

Это снимает последний структурный вопрос: весь overlay-контракт
(прозрачность, выборочный click-through, topmost, no-activate, вне Alt+Tab)
воспроизводим на Godot, причём Win32-часть — тем же кодом, что уже есть в
`NativeWindowStyles`.

Важное следствие для эргономики пилота: `WS_EX_NOACTIVATE` лишает окно
клавиатурного фокуса, то есть `ESC` перестаёт работать, а `WS_EX_TOOLWINDOW`
одновременно убирает выход через Alt+Tab — ровно та ловушка, в которую пилот
уже один раз загнал пользователя. Поэтому добавлен жёсткий автовыход через 90
секунд с обратным отсчётом прямо на экране: что бы ни сломалось дальше,
пилот не может остаться на экране навсегда.

Остаётся непроверенным: DPI/multi-monitor поведение и накладные расходы
CPU/памяти против текущих 0.73%/71.4 МБ.

## ADR-002: тестовый runner без внешних test-пакетов

Статус: принято.

Unit-проверки используют маленький консольный runner и стандартную библиотеку.
Это обеспечивает сборку без NuGet и сети. Когда появится обоснованная внешняя
инфраструктура пакетов, runner можно перенести на xUnit/NUnit без изменения
тестируемого ядра.

Обычная сборка и тесты не загружают пакеты. Self-contained публикация получает
официальные redistributable runtime packs .NET с `nuget.org`; это build-time
операция и не добавляет сетевого кода в приложение.

## ADR-003: .NET 10 LTS и self-contained win-x64

Статус: принято.

Разработка использует .NET 10. Release-публикация включает runtime, поэтому
конечному пользователю не требуется отдельно устанавливать .NET. Приложение
запрашивает обычные пользовательские права (`asInvoker`).

## ADR-004: event-driven Windows platforms с редкой сверкой

Статус: принято.

Первый snapshot строится через `EnumWindows`. Системные события передаются через
thread-safe очередь и обновляют только затронутое окно; полная сверка выполняется
раз в пять секунд. Физика получает immutable модели без Win32-структур.

Для перекрытия применяется отдельная консервативная policy верхних сегментов.
Она лучше полного игнорирования z-order, но не считается полной visible-region
композицией shaped/layered окон.

Дополнение (2026-08-02): изначальный набор хуков не включал
`EVENT_SYSTEM_FOREGROUND`, поэтому смена z-order при переключении фокуса между
окнами обновлялась только на плановой пятисекундной сверке — персонаж мог
несколько секунд стоять там, где раньше было окно, потерявшее фокус. Хук
добавлен; при получении события provider форсирует немедленный `Reconcile`
вместо ожидания интервала, сохраняя остальную event-driven модель без изменений.
